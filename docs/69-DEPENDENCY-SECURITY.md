# Зависимости разработки: minimatch и границы совместимости

Это дополнение к исторической оценке в [docs/64](64-MERGE-READINESS.md), не свидетельство проверки будущего SHA или физического устройства.

## Обновление 3 ноября: ESLint 10 без локального адаптера

`eslint@10.14.0` заменил неподдерживаемый ESLint 9. Вместо несовместимого набора `eslint-config-next` конфигурация напрямую подключает те же закреплённые Next, React Hooks и TypeScript-проверки; шесть проверок JSX-доступности выполняет `eslint-plugin-jsx-a11y-x@0.2.0`, а React/import — `oxlint@1.90.0`. Две проверки, не покрытые его реализацией целиком, сохранены локально в `scripts/lint-rules/react-policy.mjs`: старые deprecated API и анонимный `export default` через `memo`/`forwardRef`. `react/no-unsafe` дополнительно проверяет устаревшие lifecycle-методы. Обе команды lint теперь считают предупреждения ошибкой.

Временный `scripts/minimatch-compat`, его alias и ограниченный `makeRe` удалены. **Остаётся явный npm override** на upstream `minimatch@11.0.3`: ESLint 10, `@eslint/config-array`, `typescript-estree` и JSX-a11y-x пока объявляют диапазон v10. Это вынужденное пересечение major-версий, а не официальная гарантия совместимости; его нужно пересмотреть после [обновления upstream](https://github.com/eslint/eslint/issues/21463). В закреплённом наборе используются именованные `minimatch`/`Minimatch`, а не удалённый `makeRe` или старый callable default. Тесты проверяют точных потребителей, реальное разрешение модуля, несколько glob и предел раскрытия на `optimizationLevel: 2`. `npm ls` показывает override; это не подавление предупреждений peer dependencies.

Для сравнения со старой конфигурацией отдельно проверены 364 примера из тестов `eslint-plugin-react@7.37.5` с настройками по умолчанию (4 синтаксически не разобраны обеими конфигурациями), дополнительные случаи `memo`/`forwardRef` и 12 форм default export. Для шести JSX-a11y-правил сопоставлены 7581 пример из `eslint-plugin-jsx-a11y@6.10.2`: на этом наборе расхождений по факту срабатывания не было. Чистый React-набор Oxlint сначала пропускал прямой анонимный `memo` и старые deprecated API; после добавления локальных проверок среди разобранных примеров старых положительных срабатываний без нового не осталось. Это не доказательство эквивалентности всех программ и настроек. Встроенные регрессии также проверяют, что два линтера обходят один и тот же набор файлов, включая исключения generated-каталогов.

Чистая установка Node 24/npm 11 со `--strict-peer-deps`, оба `npm audit`, `npm ls eslint minimatch --all` и lint прошли локально без security/peer warnings; отдельный override остаётся указанным выше. Результаты проверок сайта и CI всегда относятся только к SHA, на котором они выполнены.

## Повторная проверка обновления группы разработки

Предложение Dependabot #135 обновляло `globals` с 14.0.0 до 17.13.0 и
`typescript-eslint` с 8.70.0 до 8.72.1, но намеренный тест точной версии
потребителя `minimatch` остановил его CI. Обновление перенесено в текущую
ветку вместе с повторной проверкой, а не с отключением этого ограничения:
`typescript-estree@8.72.1` по-прежнему вызывает именованный `minimatch` с
`dot: true`. Добавлен интеграционный тест настоящего project service для
скрытого подходящего файла и неподходящего имени с очисткой его кэша.

Между двумя версиями `globals` изменился набор имён browser/node; в продуктовом
коде не найдены использования удалённых имён. `Intl` остаётся стандартным
ECMAScript global и проверен реальным правилом `no-undef` вместе с
browser/Node и отрицательным примером. На локальном дереве оба набора линтеров
посетили 176 файлов без предупреждений; 92 эффективных правила для TSX до и
после обновления совпали. Это выборочная проверка конфигурации и репозитория,
а не обещание совместимости для произвольных проектов. Override v11 остаётся
межверсийным риском; `npm audit` не подтверждает отсутствие всех ошибок.

## История: адаптер на 1 ноября 2026

Следующие разделы описывают предыдущий подход; перечисленный в них адаптер больше не входит в текущее дерево.

## Что изменено и почему

Полный `npm audit` ранее сообщал 16 moderate-записей в dev-дереве из-за одного [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249) для `minimatch <11.0.1`. `main` содержал то же дерево; `npm audit --omit=dev` сообщал 0. `minimatch@3.1.5` не содержит описанного в advisory кода, а вызов `10.2.6` в `typescript-estree` не устанавливал `optimizationLevel >= 2`, но это не делало полный результат аудита зелёным и не гарантировало будущую конфигурацию.

Прямой override на v11 ломает старый callable CommonJS API и удалённый `makeRe`, которые используют текущие ESLint-плагины. Поэтому вместо него для запросов версий `<11.0.1` поставлен **временный локальный dev-адаптер** `scripts/minimatch-compat`. Он не содержит старую реализацию сопоставления и не подменяет номер уязвимого пакета: все фактические совпадения выполняет зафиксированный и проверяемый по lock integrity upstream `minimatch@11.0.3` через npm alias `minimatch-secure`. Адаптер и движок отсутствуют при `npm ci --omit=dev`. Новых install-lifecycle scripts нет.

v11 удалил `makeRe`; адаптер предоставляет для него только объект с `.test()` на базе `Minimatch.match()`. Именно `.test()` использует закреплённый `eslint-plugin-import`; это **не** полноценный `RegExp` и не обещание общей совместимости со всеми историческими версиями. Синтаксис и отдельные edge cases v11 также могут отличаться от v3. Не использовать адаптер как публичную библиотеку или без проверки для новых потребителей.

## Защита от ложного зелёного результата

- `npm test` проверяет точные версии всех семи потребителей, фактическое разрешение их импортов в адаптер, оригинальное имя и версию установленного upstream-пакета и отсутствие v3/v10 среди lock-записей. Новый потребитель или изменение версии существующего требуют отдельной проверки, а не молча наследуют совместимость.
- Проверяются callable CommonJS, именованные и default ESM-импорты, partial matching при обходе директорий, игнорируемые файлы и реальные правила React, JSX-a11y, import, Next и TypeScript на положительных и отрицательных примерах. Тестирование `optimizationLevel: 2` использует ограниченный процесс и проверяет upstream-предел раскрытия. Это проверка используемого контракта, не доказательство эквивалентности всех glob-паттернов.
- На исходном состоянии и с адаптером ESLint проверил те же 164 исходных файла с одинаковыми результатами; добавленные файлы проверяются отдельно. Сравнение v3/v11 на 82 152 комбинациях путей и паттернов обнаружило 22 различия для некоторых **partial**-совпадений скрытых путей при настройках без `dot: true`; общее совпадение алгоритмов не заявляется.
- В отдельном временном проекте уязвимый `minimatch@10.2.6`, установленный через npm alias, **обнаружился** полным `npm audit`. Это проверка того, что alias сам по себе не скрывает исходное имя пакета от аудита; в проекте зафиксирован `11.0.3`.
- На этом рабочем дереве полный `npm audit --audit-level=info` и `npm audit --omit=dev --audit-level=info` оба вернули **0** и код 0. CI теперь явно запускает оба аудита на каждом актуальном SHA; `npm ci`, проверки интеграции и lint остаются обязательными. Результат аудита зависит от состояния реестра на момент запуска и не доказывает отсутствие всех возможных уязвимостей.

При создании нового lock-файла npm 11 может записать ссылку локального override относительно каталога транзитивного пакета. В текущем lock ссылки нормализованы к `scripts/minimatch-compat`; после этого `npm install --package-lock-only` не изменил файл, а чистый `npm ci`, `npm ls minimatch minimatch-secure --all` и тесты прошли. При изменении зависимостей нужно снова выполнить эти команды и проверить результат на Windows/macOS, не считать одну только нулевую сумму audit доказательством работающего линтера.

## Удаление временного адаптера

Удалить override и адаптер, когда поддерживаемые upstream-версии всего набора линтера используют исправленный matcher и совместимые API; после обновления заново выполнить перечисленные проверки и сравнить эффективные правила и набор проверенных файлов. Не убирать тесты, пока действует адаптер. При необходимости миграция линтера должна сохранять проверки Next, React, TypeScript и доступности, а не просто отключать их.

На 1 ноября `eslint@9.39.5` был помечен upstream как неподдерживаемый; npm показывал предупреждение при установке. Это не было записью `npm audit`. Обычное принудительное обновление до ESLint 10 оставляло peer-конфликты старых React/import/JSX-a11y-плагинов, поэтому они были заменены и проверены описанным выше способом.
