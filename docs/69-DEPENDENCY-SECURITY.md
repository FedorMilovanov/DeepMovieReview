# Зависимости разработки: minimatch и границы совместимости

Проверка рабочего дерева — 1 ноября 2026. Это дополнение к исторической оценке в [docs/64](64-MERGE-READINESS.md), не свидетельство проверки будущего SHA или физического устройства.

## Что изменено и почему

Полный `npm audit` ранее сообщал 16 moderate-записей в dev-дереве из-за одного [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249) для `minimatch <11.0.1`. `main` содержал то же дерево; `npm audit --omit=dev` сообщал 0. `minimatch@3.1.5` не содержит описанного в advisory кода, а вызов `10.2.6` в `typescript-estree` не устанавливал `optimizationLevel >= 2`, но это не делало полный результат аудита зелёным и не гарантировало будущую конфигурацию.

Прямой override на v11 ломает старый callable CommonJS API и удалённый `makeRe`, которые используют текущие ESLint-плагины. Поэтому вместо него для запросов версий `<11.0.1` поставлен **временный локальный dev-адаптер** `scripts/minimatch-compat`. Он не содержит старую реализацию сопоставления и не подменяет номер уязвимого пакета: все фактические совпадения выполняет зафиксированный и проверяемый по lock integrity upstream `minimatch@11.0.3` через npm alias `minimatch-secure`. Адаптер и движок отсутствуют при `npm ci --omit=dev`. Новых install-lifecycle scripts нет.

v11 удалил `makeRe`; адаптер предоставляет для него только объект с `.test()` на базе `Minimatch.match()`. Именно `.test()` использует закреплённый `eslint-plugin-import`; это **не** полноценный `RegExp` и не обещание общей совместимости со всеми историческими версиями. Синтаксис и отдельные edge cases v11 также могут отличаться от v3. Не использовать адаптер как публичную библиотеку или без проверки для новых потребителей.

## Защита от ложного зелёного результата

- `npm test` проверяет точные версии всех семи потребителей, фактическое разрешение их импортов в адаптер, оригинальное имя и версию установленного upstream-пакета и отсутствие v3/v10 среди lock-записей. Новый потребитель или изменение версии существующего требуют отдельной проверки, а не молча наследуют совместимость.
- Проверяются callable CommonJS, именованные и default ESM-импорты, partial matching при обходе директорий, игнорируемые файлы и реальные правила React, JSX-a11y, import, Next и TypeScript на положительных и отрицательных примерах. Тестирование `optimizationLevel: 2` использует ограниченный процесс и проверяет upstream-предел раскрытия. Это проверка используемого контракта, не доказательство эквивалентности всех glob-паттернов.
- На исходном состоянии и с адаптером ESLint проверил те же 164 исходных файла с одинаковыми результатами; добавленные файлы проверяются отдельно. Сравнение v3/v11 на 82 152 комбинациях путей и паттернов обнаружило 22 различия для некоторых **partial**-совпадений скрытых путей при настройках без `dot: true`; общее совпадение алгоритмов не заявляется.
- В отдельном временном проекте уязвимый `minimatch@10.2.6`, установленный через npm alias, **обнаружился** полным `npm audit`. Это проверка того, что alias сам по себе не скрывает исходное имя пакета от аудита; в проекте зафиксирован `11.0.3`.
- На этом рабочем дереве полный `npm audit --audit-level=info` и `npm audit --omit=dev --audit-level=info` оба вернули **0** и код 0. CI теперь явно запускает оба аудита на каждом актуальном SHA; `npm ci`, проверки интеграции и lint остаются обязательными. Результат аудита зависит от состояния реестра на момент запуска и не доказывает отсутствие всех возможных уязвимостей.

При создании нового lock-файла npm 11 может записать ссылку локального override относительно каталога транзитивного пакета. В текущем lock ссылки нормализованы к `scripts/minimatch-compat`; после этого `npm install --package-lock-only` не изменил файл, а чистый `npm ci`, `npm ls minimatch minimatch-secure --all` и тесты прошли. При изменении зависимостей нужно снова выполнить эти команды и проверить результат на Windows/macOS, не считать одну только нулевую сумму audit доказательством работающего линтера.

## Удаление временного адаптера

Удалить override и адаптер, когда поддерживаемые upstream-версии всего набора линтера используют исправленный matcher и совместимые API; после обновления заново выполнить перечисленные проверки и сравнить эффективные правила и набор проверенных файлов. Не убирать тесты, пока действует адаптер. При необходимости миграция линтера должна сохранять проверки Next, React, TypeScript и доступности, а не просто отключать их.

`eslint@9.39.5` сейчас помечен upstream как неподдерживаемый; npm показывает предупреждение при установке. Это отдельный незакрытый вопрос поддержки инструмента, **не** текущая запись `npm audit`. Принудительное обновление до ESLint 10 без разбора нельзя считать чистым: закреплённые upstream `eslint-plugin-react`, `eslint-plugin-import` и `eslint-plugin-jsx-a11y` пока не объявляют peer-поддержку ESLint 10. Их миграция требует отдельной совместимой версии или проверенной замены, а не подавления peer-конфликта.
